# Design of the v0.1.4 gold layer contract

The milestone 0.1.4 Self Serving Gold Layer is built one issue at a time, and each issue updates the
[implementation status](#implementation-status) table when it merges. This file is the build contract of the milestone.
The [roadmap](../roadmap.md) says what the milestone is for and which issues are in it. This file says what the code
does. Where they differ about the code, this file wins.

The goal is a gold layer that people who are not engineers can use without asking an engineer. Every gold table says
who owns it, what it means, what one row is and what each column holds, all gold tables publish together as one
release, and metrics are defined once. This contract is written in the order the issues are built, so it grows by one
section for each of them.

## Contracts

### G1. Table contracts

A config can carry the contract of its table in an optional `metadata.docs` block.

```json
"docs": {
  "layer": "gold",
  "description": "Orders and revenue for each restaurant on each day it had an order.",
  "owner": "restaurant operations",
  "grain": "one row for each restaurant on each day it had an order",
  "primary_key": ["restaurant_id", "day"],
  "columns": {"restaurant_id": "The restaurant.", "day": "The day.", "orders": "How many orders."},
  "tags": ["finance"],
  "refresh": "daily"
}
```

| Key | What it holds |
|---|---|
| `layer` | `bronze`, `silver` or `gold`. Only `gold` is held to its contract |
| `description` | What the table means |
| `owner` | Who owns it. The `who` of the config when the block names none |
| `grain` | What one row is |
| `primary_key` | A column or a list of columns that identify a row |
| `columns` | Column name to description |
| `tags` | Free labels |
| `refresh` | How often it is rebuilt. The `when` of the config when the block names none |

Every text is a non-empty string, an unknown key is an error, and `null` means the key is not there. The module
`local_data_platform.contracts` has no import outside the standard library when it is imported, so the spec and the
config use it. Its public names are these.

```python
LAYERS = ("bronze", "silver", "gold")
@dataclass(frozen=True)
class Docs: layer, description, owner, grain, primary_key, columns, tags, refresh   # .gold, .properties(), .to_dict()
def docs_problems(block, *, who="") -> list[tuple[str, str]]       # (path, message), every problem at once
def parse_docs(block, *, who="", when="") -> Docs | None            # the block, normalised, with the defaults applied
def check_contract(docs, schema, *, existing=()) -> list[str]       # what is wrong with a gold table's columns
def contract_error(table, problems) -> ContractError
def apply_contract(table, docs, *, policy=None, dry_run=False, sleep=time.sleep) -> ContractResult
def docs_from_dbt_node(node, *, namespace=None, primary_key=()) -> dict
```

`Config.docs` is `parse_docs` of the block of the config, with its `who` and `when`.

**Validation.** `ldp schema` shows the block under `metadata`, and `validate_spec` and `Config` report the problems of
it, `validate_spec` all at once with the path of each. A `gold` block needs a `description` and a `grain`, and an owner
from the block or from `who`. Another layer, or no layer, needs nothing. A column called `token` or `password` is
described, not taken for a secret, but a private key pasted into a description is still caught.

**The hash.** `docs` is in `HASH_EXCLUDED_METADATA`, so editing a description does not change the spec hash. What a
run writes is the same, so nothing that hashes the spec, such as a replace key, moves.

**The gate.** Before a run writes, a gold table is checked against the columns it is about to write. A column that
has no description, or a description of a column that the table does not have, raises `ContractError`, and one message
lists every column. A column that the table already has counts, even if the new data no longer has it, and a name that
is the same as a real column in another case or one letter off comes with a hint. The check comes after the quality
checks, so a failing check is reported first, and it stops the run even when `on_failure` is `warn`. `ContractError`
is a `DataQualityError`. So `ldp run` exits with 3, a workflow marks the task `blocked_quality`, an Airflow task fails
without a retry, and nothing retries it. The run emits `run.blocked_quality` with `contract` among its `failures`, and
the problems under `contract_problems`.

**The commit.** After a run publishes, in direct and in staged mode, `apply_contract` writes the contract into the
Iceberg table. It sets the table properties `comment` (the description), `ldp.owner`, `ldp.layer`, `ldp.grain` and
`ldp.primary-key` (the columns joined with commas), and the `doc` of each described column, in one transaction. That is
a metadata-only commit, so it adds no snapshot, and it is not made at all when the table already carries every value.
It only adds and changes text. A key that is taken out of the block stays on the table. When the catalog refuses the
commit because another writer changed the table, it reloads the table, works the difference out again and tries again
after a pause, as the `CommitPolicy` allows. A run that was skipped as a duplicate writes nothing, so it does not touch
the table, and a run blocked by its quality gate writes no docs. Only an Iceberg table can carry a contract, so a run
with a file target checks it and writes nothing.

The data is published by the time the contract is written, so a contract that cannot be written is reported and does
not fail the run. The `run.published` event carries `contract` with `applied`, `changed`, the properties and columns
that changed, how many columns are documented, the described columns the table does not have, and the attempts. When
it failed it says `applied: false` and the error, and the warning is logged. `ldp gold sync` writes the contract again.

**dbt.** `ldp dbt build` fills `metadata.docs` of each generated config from `target/manifest.json`. It takes the
description of the model, the description of each column that has one, the tags, the `owner` and `grain` of the model's
meta, the key columns (the columns of an upsert, else the `unique_key`) and the layer. The layer is the meta
`ldp_layer`, else the namespace of the table when that is `bronze`, `silver` or `gold`. So a model that is published to
the `gold` namespace is a gold table. Its config is validated with the others before anything is published, so a gold
model without a description, an `owner` or a `grain` stops the build and the error names the model. A gold model with a
column that has no description stops at its own write, and the models before it stay published, as for any failed
write. `ldp dbt init` writes a gold model that has all of it.

**`ldp gold sync CONFIG`.** It writes the contract of the config into its existing table and writes no data. It
checks a gold table like a run does, so it exits with 3 when a column has no description. It exits with 1 when the table
does not exist, the config has no block, or the target is not an Iceberg table. `--dry-run` says what would change and
changes nothing, and `--json` prints the result. `--dbt-manifest FILE` is for a table that something other than LDP
built. The model of the manifest that builds the table gives the base of the block, the config's own block is written
over it key by key, and dbt is not imported. It does not need the config to say anything about the table beyond where
it is.

**What readers see.** `describe_table` of `ldp mcp` already returns the `doc` of each column and the properties of the
table, so a gold table shows its contract there with no change to the server. The robot example's two gold tables
carry theirs, and so do the gold tables of the restaurant example.

**Decisions.**

- The config is the source and the table is the copy. A person edits the block next to the pipeline, and every reader
  finds it where the data is.
- Only gold is strict, because the layer is the promise. A bronze or silver table is better documented, and nothing
  stops it being less.
- A broken contract is a data gate and not a failed run, because the cure is a person writing a sentence, and a retry
  cannot do that.
- The commit never removes anything, so a tool that wrote its own property or a doc is never undone by a run.
- Nested columns are not described. A column name is a top-level name.

### G2. SQL gold models and `ldp gold build`

**The source.** The `DUCKDB` source of 0.1.2 gets two keys, and no new format and no new route. `ldp pipelines` still
lists one `DUCKDB` to `ICEBERG` route, and a gold config runs through it with `ldp run`, like any other config.

| Key | What it says |
|---|---|
| `query_file` | A file that holds the query, in place of `sql`. A relative path is read from the folder of the config, when the source is read |
| `inputs` | A list of dataset configs, in place of `path`. The source opens an in-memory DuckDB and registers the Iceberg table that each input config writes, under the name of that table, with the session time zone set to UTC. Then it runs the query |

A source has exactly one of `relation`, `sql` and `query_file`. A `relation` needs a `path`, and `inputs` goes with
`sql` or `query_file`, never with `path` or with a `relation`. The input configs are read when the source is built, so a
missing or invalid one, one that writes a file, and two that write tables with the same name all fail there. The tables
are read when the source is read, at the snapshot that is current then, so a table that is not there yet fails with the
name of the config that writes it. A query that reads a table that is not listed fails with DuckDB's own unknown table
error, so `inputs` is the whole lineage of the table. The query goes through the same guard as `sql`, which allows one
read-only statement. `ldp plan` checks that the input configs and the query file exist. The spec hash has the paths of
`inputs` and `query_file` relative to the folder of the config, and it does not have the content of the SQL file.

**Lineage in the run events.** A run lists every table that its source was made from in `inputs` of `run.started`, as
datasets named like the target is, and the OpenLineage events list each of them as an input dataset. A source with
`inputs` says them itself, and nothing is opened to name them, so it works for a table that does not exist yet. For a
model that `ldp dbt build` publishes, the plan follows the `depends_on` of the model in the manifest. A parent that is a
source becomes the Iceberg table of that source, found in the source configs of the project. A parent that is a
published model becomes its table. A parent that is a model that is not published, such as a staging view, is looked
through to what it reads. The result is the `metadata.lineage` of the generated config, a list of `ICEBERG` blocks with
their paths relative to that config. It is for the events only, so the spec hash leaves it out, and a manifest that
cannot be followed gives none and publishes the model all the same.

**`ldp gold build DIR`.** A gold config is a dataset config with `metadata.docs.layer` `gold`. It finds them in the
`*.json` files of the folder, skips the files of another kind and the JSON that is not a config, and reports a config
that is not valid by its file name, so a typo never makes a table vanish from the build. It orders them so that a config
comes after the configs that its `inputs` name, and by file name where that leaves a choice. It refuses a cycle, and a
config that reads its own table, before it runs anything, and the message names the files.

```python
def find_gold(folder) -> list[GoldConfig]
def order_gold(found) -> list[GoldConfig]
def build_gold(folder, *, on_table=None) -> BuildResult            # .tables, .exit_code, .stopped_by, .counts()
def check_built_elsewhere(gold) -> TableOutcome
```

- A config whose source has `inputs` is built, which runs its pipeline directly, as `ldp run` does. When it names no sinks
  the `iceberg` sink is added, so the run is recorded in `_ldp.runs` and `_ldp.quality_results` of its own catalog.
- A gold config with no `inputs` is built elsewhere. It is checked, which means that its table has to exist, and that its
  quality checks run on the current snapshot, with the rows of that snapshot as the source rows, and write nothing.
- The build stops at the first table that fails or that a gate blocks, and the tables after it are `not run`. A
  `DataQualityError`, which includes a contract that does not hold, is a gate and exits with 3. Every other error exits
  with 1. A table that is built elsewhere and failed its checks is blocked too, unless the config says `warn`.
- Each table prints one line with its status, its rows, its snapshot and how its checks ended, and a last line counts
  them. `--json` prints the whole result.

**Decisions.**

- The query goes in the source, so a gold table is a config like any other. There is no model language and no second
  runner, and a person who knows SQL writes one file and one small config.
- Inputs are config files and not table names, so that a gold table finds its catalog and its own pipeline, and so that
  the build can order the gold tables without looking inside a query.
- Nothing parses the SQL for table names. The unknown table error is the check that `inputs` is complete.
- The checks of a table that is built elsewhere run where the table is, on its current snapshot, because a build that
  could not tell that a table it depends on is broken would say that everything is fine.

### G3. Gold releases

A gold table is rebuilt on its own, so two tables that are read at the same moment can come from different builds. A
release fixes that for readers. It is a version of the whole gold layer of a namespace, and a reader that reads the
current release sees every table at the snapshot that the same build ended with.

**Cutting a release.** `ldp gold build DIR` cuts release `rN` when every gold table was built or checked. Releases are
numbered from 1 for each namespace, and a number that a file holds is taken even when the file cannot be read. A release
is pinned and then written, in this order, under a lock on the namespace so that two builds on one machine do not take
one number.

1. Each table is pinned with `datasets.pin` as the dataset `<namespace>.<table>`, with the property `release=rN`, at the
   snapshot that its run ended with or that the check saw, and not at the current snapshot, so a writer that commits
   to a table in between does not change what the release names. A pin tags its snapshot, and expiry never removes
   a tagged snapshot, so `ldp maintain` keeps every released snapshot. A snapshot that cannot be tagged stops the release,
   because expiry could then remove it.
2. The release file `<warehouse>/.ldp/releases/<namespace>/rN.json` is made last. It is written to a temporary path,
   flushed, and linked into place, which fails if the number is taken, so it appears whole or not at all.

```json
{"ldp_release": 1, "release": "r3", "number": 3, "namespace": "gold", "created_at": "2026-10-15T16:07:52+00:00",
 "ldp_version": "0.1.2", "window": ["2026-08-01T00:00:00Z", "2026-08-02T00:00:00Z"],
 "workflow": {"identifier": "daily_orders", "run_id": "01a1...", "task": "gold"},
 "tables": [{"table": "gold.daily_sales", "config": "daily_sales.json", "status": "built", "snapshot_id": 123,
             "rows": 2, "dataset": "gold.daily_sales", "dataset_version": 3, "run_id": "01a1..."}]}
```

`window` and `workflow` are there only for a release that a workflow cut. A table that something else builds has the
status `checked` and no `run_id`. The rows of a table are what its snapshot has, which is not what the last write added
for an `append` or an `upsert`.

**What does not cut one.** A build that a gate blocks, or that fails, cuts none, and the last release stays current. The
output says so and names the release that readers still see. A build whose tables are at the snapshots that the current
release already names cuts none either, so a workflow that runs a window again does not pile up releases. A release that
cannot be cut after the tables were built, for example because a pin failed, is an error and exits with 1, and the
tables stay built. `--no-release` builds without cutting one.

**One namespace.** The release file lives in the warehouse of its tables, in a folder for the namespace, so a release
covers one namespace of one warehouse. A folder whose gold tables are in more than one place is refused before anything
is built, and the message says to give each place its own folder or to build with `--no-release`. A catalog with no
warehouse folder, such as a REST catalog, keeps its releases in `$LDP_WAREHOUSE` when it is set.

```python
@dataclass(frozen=True) class Release: name, number, namespace, created_at, tables, window, workflow, path
def cut_release(tables, *, context=None, sink_for=None) -> ReleaseOutcome
def list_releases(folder) -> list[Release]                              # newest first
def current_release(folder) -> Release | None
def get_release(folder, name) -> Release
def choose_release(folder, *, release=None, live=False) -> Release | None
def snapshot_for(table, release) -> int | None
def release_snapshots(folder, *, release=None, live=False) -> dict[str, int]
def register_release(engine, folder, *, release=None, live=False) -> dict[str, int]
```

**What readers do.** Every reader of the gold layer follows one rule. It reads the current release by default,
`--release rN` reads an older one, and `--live` reads the tables as they are now. A table that is in no release, and a
folder that has no release yet, are read at the current snapshot. `choose_release` is that rule, `snapshot_for` gives the
snapshot to pass as `snapshot_id` to `DuckDBEngine.register_iceberg`, and `register_release` does it for every gold table.
`ldp query` is the one reader that exists in this item. It takes `--release` and `--live`, and it keeps reading live when
neither is given, because it is the general tool for looking at any table, so `--live` only says what it does anyway. It
leaves a table alone when the namespace of the table has no releases, so the silver tables of a query are read as they
are. The readers that later items add use the rule with the current release as the default.

**Run events.** Each table of a release gets a `release.cut` event in the run events of its own catalog, or in the sinks
of its config, as a run of its own with the table's pipeline name. `ldp runs` shows it with the status `released`, the
release and the snapshot, so the history of a table says when it was released and in which release. The OpenLineage sink
leaves these events alone, because a release is not a run of a job.

**The `gold` task.** A workflow can run the build and the release as a task, `{"gold": {"dir": "config"}}`. It runs the
gold configs of the folder in order for the window of the run, each as a `pipeline` task runs a config. An Iceberg table
is written under the idempotency key of the window, so the same window again finds every table already published and writes
nothing, and a replace run writes it again under the replace key and needs a `window.column` in the config, as a pipeline
task does. Each table has a run id of its own, the same for every attempt of the task, so a retry fences the attempt
before it. The task ends `succeeded`, `skipped_duplicate` when it wrote nothing and cut nothing, `blocked_quality` when a
gate held a table back, or `failed`. A folder with no gold config yet is a warning in the plan and a failure when the
task runs, because a dbt task before it may write the configs of the models that it publishes, and the workflow of the
restaurant example keeps them in the folder of its other configs. The events of its tables, and the `release.cut` events, carry the workflow, the run
and the task.

**Decisions.**

- A release is a file next to the data and not a table in the catalog, so it needs no catalog that supports transactions
  across tables, and it works on every catalog that keeps its warehouse in a folder.
- The pins give the release its protection, and the file gives it its consistency. The file is authoritative, and a pin
  that a failed cut left is a valid dataset version that no release names.
- A release is cut only when it differs from the current one, so cutting is safe to repeat.
- There is no way yet to remove an old release. Its tags keep its snapshots, and with them their files, until a later
  command lets them go.

### G4. The gold catalog

A person who is not an engineer should find the right gold table without reading pipeline code, and so should an agent
that works for them. The catalog is one entry for each table of a folder of configs. `ldp gold list`, `show` and `docs`
print the entries, and 0.1.8 search reads them as its documents.

**The entries.** The tables are the Iceberg targets of the dataset configs of a folder. `ldp query DIR` reads these tables
and the Iceberg sources of the configs too, and a source that no config of the folder writes is not an entry. A table that
two configs write is described by the one that has a contract. The catalogs are only read. A catalog that does not exist is not created, a
namespace that does not exist is not created, and a table that does not exist yet is an entry that says so.

```python
@dataclass(frozen=True) class CatalogEntry: table, namespace, name, layer, description, owner, grain, primary_key, tags,
    refresh, config, exists, columns, snapshot_id, rows, refreshed_at, run, quality, release, release_state, problems,
    notes, metrics, detailed, runs, releases, sample, query
def collect(folder, *, all_layers=False, only=None, detail=False, runs=5, sample=5, now=None) -> Catalog
def resolve_table(identifiers, text, folder="") -> str
def query_line(folder, identifier, limit=10) -> str
CatalogEntry.document() -> str                  # the words of the entry, which search indexes
Catalog.lacking / .lacking_summary / .find(table) / .to_dict()
```

**The contract of an entry.** It is the contract of the config and the contract that the Iceberg table carries,
`contracts.read_contract`, field by field. The config wins where both have a value, because it is what the next run
writes, and the entry says so, with the command that fixes it, when the table does not carry the whole of it yet. The
table fills in what the config leaves out, so a config with no `docs` block still shows what the table says. `tags` and
`refresh` are only in the config. The layer is `contracts.resolve_layer`, the first of the layer the config declares, the
`ldp.layer` of the table and the namespace when it is called `bronze`, `silver` or `gold`. A table with no contract is an
entry with no description. Its description is `null` in JSON and `no description` in text, a page and Markdown.

**What a gold table lacks.** A gold table has a description, an owner and a grain, and a description of each column. An
entry lists what it lacks as `problems`, such as `no owner` or `3 columns without a description (a, b, c)`, and
`lacks_text` says it as a sentence. A table of another layer lacks nothing. A gold table can lack its contract because it
is in a namespace called `gold` and has no `docs` block, or because something other than LDP built it and nobody ran
`ldp gold sync`.

**How it is doing.** `rows` and `snapshot_id` are the table as it is now. `refreshed_at` is the time of the newest
snapshot on `main` that is not a rewrite by `ldp maintain`, so compacting a table does not make it look fresh. The run and
the quality are `gold.status.ldp_status`, which `describe_table` of `ldp mcp` calls too, so the two report the same
status. `release` is the release that readers see now, when it holds the table, and `release_state` is `current` when the
table is at its snapshot there and `behind` when the table was built again after it. Nothing here reads the data of a
release. The catalog describes the tables as they are, and `ldp query` and the exports that come later are the readers
that follow the rule of G3.

**The status of a table.** `_ldp.runs` has the events of each table, and a release cut after a build adds a `release.cut`
event as a run of its own, with the same table and pipeline. The status code leaves it out of the runs, because it is not a
run of the pipeline. Before this issue `describe_table` took it for the latest run of a released table and said `running`.
`recent_runs` lists the last runs, newest first, with a retried task as one run for each attempt.

**The commands.**

- `ldp gold list DIR` has one row for each gold table. `--all-layers` adds the other tables and the layer column, `--json`
  prints the catalog as data, and `--strict` exits with 1 when a gold table lacks any part of its contract, and says which.
  It is a check of the metadata, so it is an error and not a data gate, and exit status 3 stays for what a run holds back.
- `ldp gold show DIR TABLE` describes one table, found by its identifier or by its bare name when only one table has it. It
  has the contract, every column with its type and description, the metrics defined on the table, the last 5 runs, the
  releases that include it, 5 sample rows and the `ldp query` line that reads it. `--runs N` and `--no-samples` change
  that. There are no metrics until G5 defines them, so `metrics` is empty, and the part of the output that lists them is
  left out.
- `ldp gold docs DIR --out FILE` writes the same content as one page, or as Markdown with `--format md`. `--out` is
  required, so that no file is written by surprise, and `-` is standard output. The file is written to a temporary path and
  renamed. The sample rows are in it unless `--no-samples` leaves them out, because a page that is shared should not have to
  carry rows that must not be.

**The page.** `html.py` is the one page shell of the project. It is made of three promises that 0.1.5 and 0.1.6 keep too.
The page is one file, with its CSS and its one script inline, and a Content-Security-Policy of `default-src 'none'` that
allows its style and its script by their hashes, so the browser refuses any request. Its colours are tokens on `:root`,
and the dark ones follow `prefers-color-scheme`. And markup is built with `h()`, which escapes every attribute value and
every text child unless the child is the `Raw` that a call of `h()` made, so a value that a person wrote can never become
markup. The search box filters the cards by the words of `data-search`, which is the lower case document of each entry. The
Markdown escapes `&`, `<` and `>` as entities and the characters that Markdown reads with a backslash.

**In `ldp mcp`.** `list_tables` returns `layer`, `description`, `owner` and `grain` for each table, and `null` for what a
table does not say. `describe_table` returns the contract. It has the same four, the `primary_key` as a list, `columns` as a map
of name to description and `undocumented_columns`. It is read from the Iceberg table, so it is the same for every client,
and the config of a table that the table does not carry yet is not made up. `--layer {bronze,silver,gold}` serves only the
tables of one layer, found with `discover_tables(layer=...)`, so no tool and no SQL can reach the others. The layer of a
table is the one rule above, and a table that is not in the layer is not an unavailable table.

**Decisions.**

- The config wins over the table, and the entry says so. A catalog is read to learn what the owners declared, and the
  warning says that readers of the table do not see it yet.
- JSON has `null` for what is missing, so that a consumer can test for it, and the placeholder `no description` is only for
  people.
- `--strict` exits with 1 and not 3. It checks metadata, and the exit status of a data gate belongs to what a run held back.
- The catalog says whether a release holds a table and whether the table is ahead of it, and it does not read the release.
  The sample rows are the current ones.
- An entry is only for a table that a config of the folder writes, as `ldp query` reads them. A table that someone else
  wrote into the same warehouse is not listed until a config names it.
